# Проект «Табло теннисного матча»

Веб-приложение, реализующее табло счёта теннисного матча.

## 1. Общие сведения

- Комментарии по проекту: <https://www.youtube.com/watch?v=zAOiNa24jpg>
- Обсуждение работы над проектом:
  - Основной чат сообщества: <https://t.me/zhukovsd_it_chat>
  - Чат по работе над проектами (каждому проекту посвящена отдельная ветка): <https://t.me/zhukovsd_projects_it_chat>

**Комментарии:**

- Проект не многопользовательский, поэтому **сессии не используются**.
- Проект подразумевает **REST API**.
- Незавершённые матчи хранятся в **потокобезопасной коллекции в памяти** приложения (для практики многопоточности).
- В БД сохраняются **только завершённые матчи** — в момент их завершения.

## 2. Цели проекта

- Написать относительно сложную бизнес-логику, познакомиться с богатой доменной моделью.
- Научиться покрывать бизнес-логику тестами.
- Получить практический опыт работы с ORM Hibernate.

## 4. Функциональные требования

Работа с матчами:

1. Создание нового матча.
2. Подсчёт очков в текущем матче.
3. Просмотр завершённых матчей.
4. Поиск завершённых матчей по именам игроков.

## 5. Правила подсчёта очков

В теннисе особая система подсчёта очков. Подробности: <https://www.gotennis.ru/read/world_of_tennis/pravila.html>

Для упрощения каждый матч играется по следующим правилам:

- Матч играется **до двух выигранных сетов** (best of 3).
- При счёте **6/6 в сете** играется **тай-брейк до 7 очков**.

## 6. База данных

В качестве СУБД используется **PostgreSQL**. Для разработки потребуется локально установленный Postgres либо запущенный через Docker.

### 6.1. Таблица `Players` — игроки

| Колонка | Тип | Комментарий |
|---|---|---|
| `ID` | Int | Первичный ключ, автоинкремент |
| `Name` | Varchar | Имя игрока |

**Индексы:**

- Уникальный индекс по колонке `Name` — для эффективного поиска игроков по имени и запрета повторяющихся имён.

### 6.2. Таблица `Matches` — завершённые матчи

| Колонка | Тип | Комментарий |
|---|---|---|
| `ID` | Int | Первичный ключ, автоинкремент |
| `Player1` | Int | ID первого игрока, внешний ключ на `Players.ID` |
| `Player2` | Int | ID второго игрока, внешний ключ на `Players.ID` |
| `Winner` | Int | ID победителя, внешний ключ на `Players.ID` |

## 7. REST API

### 7.1. Формат ответа при ошибке

Для всех запросов в случае ошибки ответ имеет вид:

```json
{
    "message": "Имена игроков не могут совпадать"
}
```

Значение `message` зависит от того, какая именно ошибка произошла.

### 7.2. Создание нового матча

`POST /matches`

**Тело запроса** (`Content-Type: application/json`):

```json
{
  "firstPlayerName": "First Player",
  "secondPlayerName": "Second Player"
}
```

**Успех:** `201 Created`

```json
{
  "id": "1d5e5fb4-5203-4933-8278-486f3d8db2ca"
}
```

**Коды ошибок:**

| Код | Причина |
|---|---|
| 400 | Ошибки валидации |

### 7.3. Начисление очка

`POST /matches/{uuid}/point`

**Параметры пути:** `uuid` — идентификатор матча.

**Тело запроса** (`Content-Type: application/json`):

```json
{
  "name": "First Player"
}
```

**Успех:** `200 OK`

Ответ содержит вложенные объекты `firstPlayer` и `secondPlayer`, каждый из которых описывает счёт конкретного игрока.

В обычном гейме поле `tieBreakPoints` равно `null` (или отсутствует в JSON):

```json
{
  "firstPlayer": {
    "name": "First Player",
    "points": "40",
    "games": 2,
    "sets": 0,
    "tieBreakPoints": null
  },
  "secondPlayer": {
    "name": "Second Player",
    "points": "AD",
    "games": 3,
    "sets": 1,
    "tieBreakPoints": null
  },
  "winnerName": null
}
```

В тай-брейке поле `points` равно `null` (или отсутствует в JSON):

```json
{
  "firstPlayer": {
    "name": "First Player",
    "points": null,
    "games": 6,
    "sets": 0,
    "tieBreakPoints": 5
  },
  "secondPlayer": {
    "name": "Second Player",
    "points": null,
    "games": 6,
    "sets": 0,
    "tieBreakPoints": 4
  },
  "winnerName": null
}
```

**Коды ошибок:**

| Код | Причина |
|---|---|
| 404 | Матч с таким `uuid` не найден |

### 7.4. Получение счёта

`GET /matches/{uuid}`

**Параметры пути:** `uuid` — идентификатор матча.

**Успех:** `200 OK`

Формат ответа идентичен ответу на `POST /matches/{uuid}/point` (см. п. 7.3), включая варианты для обычного гейма и тай-брейка.

**Коды ошибок:**

| Код | Причина |
|---|---|
| 404 | Матч с таким `uuid` не найден |

### 7.5. Список завершённых матчей

`GET /matches`

**Параметры запроса:**

| Параметр | Тип | Обязательность |
|---|---|---|
| `page` | число | необязательный |
| `player_name` | строка | необязательный |

**Успех:** `200 OK`

```json
{
  "matches": [
    {
      "firstPlayerName": "First Player",
      "secondPlayerName": "Second Player",
      "winnerName": "Second Player"
    },
    {
      "firstPlayerName": "First Player",
      "secondPlayerName": "Second Player",
      "winnerName": "First Player"
    }
  ],
  "currentPage": 0,
  "totalPages": 10
}
```

## 9. Архитектура: богатая доменная модель

В предыдущем проекте вся архитектура без проблем вписывалась в классический MVC(S). В данном проекте появляется относительно сложная бизнес-логика (подсчёт очков). Если описывать её целиком в сервисе (условно, `ScoreCalculationService`), такой класс быстро «распухнет», станет тяжёлым для чтения и модификации.

Поэтому применяется подход **богатой доменной модели**: бизнес-логика описывается напрямую в классах-моделях, привязанных к сущностям предметной области. Такие классы могут описывать стадии теннисного матча: `Match`, `Set`, `Game` и т. д.

## 10. Тестирование

Подсчёт очков в матче покрывается юнит-тестами. Набор тестов реализуется с помощью **JUnit 5**.

**Примеры кейсов:**

- Если игрок 1 выигрывает очко при счёте 40–40, гейм не заканчивается.
- Если игрок 1 выигрывает очко при счёте 40–0, он выигрывает и гейм.
- При счёте 6–6 начинается тай-брейк вместо обычного гейма.

Тест-кейсы для покрытия всех вариантов изменения счёта в матче (особенно правила «больше-меньше» и тай-брейк) разработчик придумывает самостоятельно.

## 11. Деплой

Артефакт `war` деплоится вручную в Tomcat, установленный на удалённом сервере. На сервер также необходимо установить PostgreSQL.

**Шаги:**

1. Локально собрать `war`-артефакт приложения.
2. Арендовать облачный Linux-сервер у хостинг-провайдера по выбору.
3. Установить JRE и Tomcat.
4. Установить Postgres и настроить доступы (можно воспользоваться Docker).
5. Зайти в админский интерфейс Tomcat и установить собранный `war`-артефакт.

**Ожидаемый результат:** приложение доступно по адресу `http://$server_ip:8080/$app_root_path`.
